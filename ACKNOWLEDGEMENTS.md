## Test material

A tool that inspects depth maps is only as good as the depth maps it has been pointed at, and
files made deliberately as test cases are the easy ones. Real work — made by someone solving a
real problem, not demonstrating a defect — is what finds the gaps. DepthView has been checked
against depth maps from working engravers, and one of those files is the reason the level
threshold in `DepthAnalyzer` is calibrated the way it is: a fixture with a known answer can
tell you a measurement is wrong, but never that a correct measurement is being reported with
the wrong emphasis. Thanks to everyone who let their work be pointed at.

**No third-party depth map is distributed in this repository.** Those files belong to the
people who made them, and being allowed to test against something is not permission to
republish it. `samples/` is an allow-list in `.gitignore` for exactly that reason: everything
dropped in that folder is ignored unless it is named explicitly.

The sample depth maps in [`samples/`](samples/) are generated by `samples/make_samples.py` and
are original to this project.

## Correcting the record

Two findings in DepthView exist because people on the LightBurn forum read the announcement
thread carefully enough to argue with it.

**Nathaniel Klumb** — twice. First for catching that LightBurn 2.1 added 16-bit depth map
support, at a point where a quote about a 256-level ceiling had been accepted here without
checking which version it described. The original README was right and the correction was the
error; the lesson, written into `TODO.md` where the next person will trip over it, is that an
authoritative-sounding quote still has a date on it.

Then for the argument behind the **band spread** column. The reading that 16 bits only matter
beyond 256 passes is about how many depths a file *contains*; Nathaniel pointed out that it
also changes how evenly those depths are *spaced*. A slicer cuts the level range into equal
bands, levels are integers, so unless the pass count divides the range exactly some bands hold
more levels than others. With 256 levels, only the powers of two divide evenly — eight pass
counts out of 255 — while half of them leave some terraces twice as wide as their neighbours.
A genuine 16-bit map stays within 0.4% anywhere in that range. His arithmetic reproduced
exactly, and the measurement it prompted turned out to be the second thing an imposter costs
you, which this tool had not been reporting.

**Jack Wilborn** — for pressing the documentation's own wording hard enough to make the
distinction between the two arguments worth drawing out. Disagreement that stays with the
source text is more useful than agreement that does not.

## Prior art and context

**LightBurn Software** — for the 3D Sliced Image mode DepthView is largely aimed at, and for
documentation candid enough to state where its depth control ends. Several of DepthView's
findings exist specifically because LightBurn's own documentation is honest about the limits.

**The WeCreat Lumos Ultra community** — for working out in public what a 256-layer relief
actually needs from its source image, well before any tool was checking.

**WeCreat support** — for engaging seriously with detailed technical reports and correcting
two published Lumos Ultra specifications as a result: the UV spot size, and the fact that the
256-depth-layer figure is an 8-bit software representation rather than a controller limit.
That second correction is load-bearing here — it is part of the reasoning behind the level
threshold in `DepthAnalyzer`. A vendor who answers numbered questions properly and amends
their own documentation is rarer than it should be.
